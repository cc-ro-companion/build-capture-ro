# Build planner — plan

Status: approved

Source idea: [ideas/build-planner.md](ideas/build-planner.md). That file holds
the product decisions; this file holds the order of work. Each phase gets its
own detailed plan (`docs/phase-<n>-<topic>-plan.md`) when it starts; this file
stays at phase level on purpose.

## Goal
Ship a public, Path of Building inspired build planner for the ccRO
community: plan a character in the desktop browser, pick a target monster,
and see damage dealt and damage taken. No login, no backend, hosted on GitHub
Pages as an offline-capable PWA, builds shared as codes. Launch as 1.0 once
the numbers hold up against ccRO's training dummy.

## Out of scope
- Rebirth jobs, renewal mechanics, servers other than ccRO.
- Mobile layout, translations (data is only modelled for them).
- Gameplay simulation, movement, per-build revision history.
- Login, backend, in-app feedback channel.

## Design

### Decisions taken for this plan
| Decision | Choice | Reason |
| --- | --- | --- |
| Stack | Svelte 5 + TypeScript + Vite | Fine-grained reactivity suits a calculator where one change updates many numbers; small bundle. |
| Phase order | Vertical slice first, then widen | Formula validation against the training dummy starts early instead of after everything is built. |
| Pre-1.0 hosting | Deployed to GitHub Pages from phase 1, marked as unfinished, not announced | Deploy, PWA and asset pipeline are exercised for the whole project, not just before launch. |
| ccRO data | Entered by hand as an override layer | No server db is available. The maintainer has data prepared; the core is runes (instead of vanilla cards), the card system and costumes, so the volume is manageable. |
| rAthena base | The local checkout at `D:\Gits\rathena` (`7f080871`, 2026-06-18 when this plan was written), `db/pre-re` | Pre-renewal data has been stable for years, so the exact commit matters little. Re-evaluate only if validation shows something odd. |

### Defaults assumed (not asked; change if wrong)
- Package manager pnpm, tests with Vitest, lint with ESLint + Prettier,
  type check with `svelte-check`.
- Plain Svelte + Vite single-page app, no SvelteKit: there is no routing or
  server rendering to justify it.
- The calculation engine is plain TypeScript with no UI imports, so it can
  be unit tested and later moved into a web worker if "what if" comparisons
  need it.
- Game data is generated by scripts from the rAthena checkout into typed
  JSON; generated data is not edited by hand. ccRO changes live in separate
  override files that the generator merges on top. The generator records
  the rAthena commit it read, so a data version can be traced back.
- Every validated character from a training dummy session is recorded as a
  test fixture (build + expected numbers), so validated formulas cannot
  regress silently.

### Layout
```
data-pipeline/   scripts: rAthena YAML + ccRO overrides -> typed JSON
data-overrides/  hand-maintained ccRO differences
src/engine/      formulas and effect model, pure TypeScript
src/build/       build state model, share codes, storage
src/app/         Svelte UI
tests/fixtures/  validated characters with expected numbers
```

## Phases

Each phase ends with something usable in the deployed app and, from phase 2
on, a validation session against the training dummy.

1. [x] **Foundation.** Project scaffold, license (GPL-3.0, rAthena credit,
   disclaimer), CI (type check, lint, tests, build), GitHub Pages deploy with
   an "unfinished" banner, empty app shell with the layout above.
2. [x] **Data pipeline, first cut.** Read `db/pre-re` from the local
   rAthena checkout (how CI gets the data is decided here). Generate typed
   JSON for what the slice needs: jobs (stat bonuses, base ASPD, weapon
   types), items (weapons first), monsters, size and element tables. Define
   the override layer format and the data version.
3. [ ] **Vertical slice: auto attack.** One character (job, level, job level,
   stats with point budget), one weapon picked by search, a target monster,
   and the auto attack result: min/max/average, hit chance, crit, ASPD, DPS.
   Includes the build state model, saving in the browser, and share codes
   with data version. First validation session.
4. [ ] **Equipment and effects.** All equipment slots, refinement, the
   effect model, and the conversion of rAthena item scripts into effects.
   Runes, combos, and the per-build inventory of configured items. The
   script conversion is the largest unknown of the project; its approach is
   decided at the start of this phase.
5. [ ] **Skills.** Skill trees with point budget and prerequisites, passive
   skills, offensive skills (physical, then magical), multi-hit display,
   cast time and cast delay, ammo with element. Done job by job for the
   base first and second jobs.
6. [ ] **Buffs, consumables, debuffs.** Own and party buffs, cooking, ASPD
   potions, converters, scrolls, mounts, pet bonuses, monster debuffs.
7. [ ] **Expanded classes.** Taekwon, Star Gladiator, Soul Linker, Ninja,
   Gunslinger, Super Novice, each with its special mechanics.
8. [ ] **ccRO features.** Card system (album with collection bonuses),
   costumes, ccRO consumables, ccRO specialities, Scaled Dungeon monsters.
   Data is entered by hand from the maintainer's prepared material; settles
   how it is kept current per patch. (Runes are already in phase 4.)
9. [ ] **Damage taken.** Monster auto attacks and skills against the
   player's DEF/MDEF, flee, perfect dodge, armor element and reductions.
   Needs monster skill data in the pipeline.
10. [ ] **Comparisons and build management.** "What if" previews on hover
    and tick, plus duplicating, organizing, exporting and importing builds.
11. [ ] **Assets and PWA.** Sprite and icon extraction, the external asset
    store pulled in at build time, service worker with precache, offline
    use, installability.
12. [ ] **Launch 1.0.** Full validation pass over all jobs, performance
    pass on search and filtering, changelog, remove the banner, announce.

Phases 6 to 9 are independent of each other and can be reordered. Phase 11
can move earlier if the app feels bare without sprites during validation.

## Acceptance criteria
- [ ] Every item under "Build contents", "Target monster" and
      "Calculations" in the idea file is available in the deployed app.
- [ ] All supported jobs have at least one validated fixture whose numbers
      match the training dummy.
- [ ] A share code created in one browser restores the same build and the
      same numbers in another, and shows the data version hint when the data
      has changed since.
- [ ] After the first visit the app starts and works with the network off.
- [ ] Item and monster search stay responsive while typing over the full
      data set.

## Verification
Per phase, once the scaffold exists:
```
pnpm check && pnpm lint && pnpm test && pnpm build
```
Formula correctness cannot be proven by a command alone: the maintainer
compares against ccRO's training dummy, and the results become fixtures that
`pnpm test` then guards. Trying the deployed app in the browser is the
maintainer's step.

## Open questions
- ~~How CI and the Pages deploy get the rAthena data.~~ Decided in phase 2:
  the generator runs locally and the generated JSON is committed.
- ~~Share code format.~~ Decided in phase 3: versioned build JSON,
  `deflate-raw` via `CompressionStream`, base64url, in the URL fragment
  `#b=<code>` (see [phase-3-auto-attack-plan.md](phase-3-auto-attack-plan.md)).
- Script conversion approach: parse rAthena scripts automatically, convert
  by hand, or a mix. Phase 4.
- Format of the hand-entered ccRO data (runes, card system, costumes) and
  where the maintainer's prepared material comes in. Runes in phase 4, the
  rest in phase 8.
- Asset store and how the deploy workflow authenticates to it. Phase 11.
- Scaled Dungeon monsters: one picker or a separate section. Phase 8.
